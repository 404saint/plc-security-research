# OpenPLC Runtime v4 Architecture Research Primer

## Executive Summary

OpenPLC Runtime v4 is an open-source, software-based programmable logic controller designed to execute industrial control applications on general-purpose computing platforms. It provides the execution environment for PLC programs and exposes management and debugging capabilities through an API-driven architecture.

Unlike a conventional PLC whose control functions are delivered as an integrated hardware product, a software PLC combines application execution with the resources and interfaces of its host operating system. Its security therefore depends on the runtime itself, the control application it executes, the mechanisms used to manage it, and the environment in which it operates.

OpenPLC Runtime v4 uses a dual-process architecture. A REST API server handles communication with the OpenPLC Editor and coordinates runtime management, while a separate C/C++ execution core runs PLC applications. The two processes communicate through local Unix domain sockets. The runtime also provides a plugin system for extending its I/O capabilities.

This architecture creates several related areas of interest:

- The **execution model** responsible for evaluating PLC applications.
- The **management interface** used to configure and control the runtime.
- The **internal communication layer** connecting management and execution.
- The **I/O architecture** connecting logical control operations to external interfaces.
- The **host environment** supplying operating-system resources, privileges, and isolation mechanisms.

These components establish the architectural vocabulary required for the PLC Security Research series. The objective of this primer is to explain their roles and relationships without attempting to reproduce the runtime's complete implementation or preempt the investigations that follow.

The architecture described here is based on the OpenPLC Runtime v4 project documentation. Implementation-specific properties must still be verified against the exact version deployed in the laboratory.

**Primary reference:** [OpenPLC Runtime v4 source repository](https://github.com/Autonomy-Logic/openplc-runtime).

# 1. OpenPLC in the Industrial Control Model

A programmable logic controller evaluates a control application and uses its results to influence a physical or simulated process. Its operation connects application logic, process inputs, output commands, and the interfaces through which those values are exchanged.

OpenPLC implements this control model in software. Instead of depending exclusively on a dedicated PLC hardware platform, the runtime executes on a supported host operating system and uses available software and hardware interfaces to interact with its environment.

The broader control relationship can be represented as:

```text
       Engineering Environment
                  |
                  | Program preparation
                  v
          PLC Control Program
                  |
                  | Deployment
                  v
          OpenPLC Runtime
                  |
                  v
          Input / Output Layer
                  |
                  v
       Physical or Simulated Process
```

The diagram represents the conceptual relationship between engineering, execution, and process interaction. It does not imply that every stage is implemented as a separate process or that all I/O is physical.

The engineering environment prepares the application, the runtime executes it, and the I/O layer connects its logical values to the available interfaces.

These responsibilities are related but distinct. The control application defines the intended behavior, while the runtime supplies the execution environment and mechanisms needed to make that behavior operational.

OpenPLC Runtime v4 is designed to work with OpenPLC Editor v4. The editor and runtime therefore form parts of a broader system, even though they operate as separate software components.

# 2. Runtime Architecture

OpenPLC Runtime v4 documents a dual-process design that separates runtime management from PLC execution.

The architecture consists of two principal processes:

- **REST API server:** A Python application built around Flask that provides the management API, WebSocket debugging interface, and coordination of runtime operations.
- **PLC runtime core:** A C/C++ execution engine responsible for running PLC applications and managing their operational state.

The documented architecture can be represented as:

```text
+------------------------------------------+
|            OpenPLC Editor v4             |
+------------------------------------------+
                     |
                     | HTTPS / REST API
                     | WebSocket debugging
                     v
+------------------------------------------+
|          REST API Server Process         |
|                                          |
|  Authentication / Management / Debugging |
|  Program handling / Runtime coordination |
+------------------------------------------+
                     |
                     | Unix domain sockets
                     |
              +------+------+
              |             |
              v             v
       Command / Control   Log Streaming
              |             |
              +------+------+
                     |
                     v
+------------------------------------------+
|            PLC Runtime Process           |
|                                          |
|  Program loading / Execution / I/O       |
|  Runtime state / Scan-cycle processing   |
+------------------------------------------+
                     |
                     v
+------------------------------------------+
|           I/O Plugin Layer               |
+------------------------------------------+
                     |
                     v
+------------------------------------------+
|       Host Interfaces / Process I/O      |
+------------------------------------------+
```

This diagram summarizes the documented component relationships. It is not a verified process map of the running laboratory target, and it does not establish the exact privilege separation or security properties of each component.

The architectural difference is important because management and execution perform different jobs. The API server handles external interaction and coordinates operations, while the execution core is responsible for running the control application.

Separating these functions into processes provides an operating-system boundary between their memory spaces. However, separate processes alone do not establish complete security isolation. The effective boundary also depends on process privileges, filesystem permissions, socket access, and the mechanisms through which the processes communicate.

The actual process configuration and enforcement mechanisms are subjects for the corresponding investigation phases.

# 3. The PLC Execution Model

The PLC runtime's central responsibility is to execute a control application and connect its evaluation to the state of the process being controlled.

PLC execution is commonly described through a recurring scan cycle:

```text
          +-------------------+
          |   Read Inputs     |
          +-------------------+
                    |
                    v
          +-------------------+
          | Execute Control   |
          |      Logic        |
          +-------------------+
                    |
                    v
          +-------------------+
          |   Update Outputs  |
          +-------------------+
                    |
                    v
               Repeat
```

At a conceptual level, input acquisition supplies the values available to the application. The control logic evaluates those values together with its internal state, and the resulting output values are applied through the configured I/O mechanisms.

The scan cycle provides a useful model of control execution, but it should not be confused with a guarantee of deterministic behavior under every operating condition.

Several properties influence the behavior of a software PLC:

- **Execution correctness:** Whether the loaded application evaluates and produces the expected logical results.
- **Cycle timing:** How long each execution cycle takes and how consistently the cycle repeats.
- **Scheduling:** How the operating system allocates processor time to the execution work.
- **I/O behavior:** How input acquisition and output updates interact with devices and external interfaces.

OpenPLC Runtime v4 documents the use of real-time scheduling through `SCHED_FIFO` for its execution core. This is relevant to how the runtime competes for processor time, but the presence of a real-time scheduling policy does not independently prove that every application will meet a particular deadline. Actual timing depends on the runtime implementation, host configuration, workload, I/O behavior, and other environmental factors.

The detailed execution loop, thread activity, and scheduling configuration must be examined against the deployed target rather than inferred from the general scan-cycle model.

# 4. Management Interface and Runtime Control

OpenPLC Runtime v4 is designed as a headless service controlled through the OpenPLC Editor. Rather than relying on the legacy runtime's browser-based management model, v4 exposes a REST API for program management, runtime status, and related operations.

The documented management path is:

```text
       OpenPLC Editor v4
                 |
                 v
          HTTPS / TCP 8443
                 |
                 v
          REST API Server
                 |
                 v
         Runtime Management
                 |
                 v
          PLC Runtime Core
```

The API server also supports a WebSocket debugging interface used by the editor for real-time interaction with PLC variables.

The documented API uses JWT-based authentication, and the management service is exposed over HTTPS. These mechanisms establish the intended interface model, but their presence does not prove that every endpoint is correctly protected or that the deployed configuration provides an appropriate security boundary.

The difference between the management interface and the execution core is important because an external client interacts with the runtime through the service layer rather than directly through the internal execution implementation.

Consequently, several different questions arise:

- Which operations are available through the API?
- How is client identity established and authorization enforced?
- How are management requests translated into operations on the execution core?
- What happens when the execution core becomes unresponsive?
- Which debugging capabilities can affect runtime state?

Those questions require direct investigation. This primer establishes the management interface's role without analyzing its endpoints or evaluating its authentication and authorization behavior.

Reference: [OpenPLC Runtime v4 API documentation](https://github.com/Autonomy-Logic/openplc-runtime/blob/main/docs/API.md).

# 5. Internal Communication Between Components

The REST API server and PLC execution core operate as separate processes. They therefore require a mechanism for exchanging commands, status information, and other internal data.

OpenPLC Runtime v4 documents the use of **Unix domain sockets** for this communication.

A Unix domain socket provides a local communication endpoint within the host operating system. Unlike a TCP socket, it does not require the communicating processes to exchange data through an IP network interface.

The documented communication relationship can be summarized as:

```text
       REST API Server
              |
              |
      +-------+-------+
      |               |
      v               v
 Command / Control   Runtime Logs
      |               |
      v               v
 PLC Runtime Core
```

The project documentation identifies separate socket paths for command/control communication and runtime log streaming. These channels allow the management process to coordinate with the execution core without requiring every internal operation to be exposed through a network-facing API.

This creates an architectural difference between external and internal communication:

- **External communication** connects the editor or another API client to the management service.
- **Internal communication** connects the management service to the execution core.
- **Execution activity** takes place within the PLC runtime process.

The difference is relevant to security because each channel has its own access conditions and trust assumptions.

For example, network authentication governs access through the management API, whereas access to a Unix domain socket can depend on filesystem permissions and the privileges of the processes involved. These mechanisms protect different boundaries and should not be treated as interchangeable.

The precise socket permissions, message formats, validation behavior, and failure handling remain subjects for direct examination.

Reference: [OpenPLC Runtime v4 architecture and source](https://github.com/Autonomy-Logic/openplc-runtime).

# 6. Program Preparation, Loading, and Execution

The runtime does not operate independently of the PLC application supplied to it. Its purpose is to load and execute control logic prepared through the supported programming workflow.

OpenPLC Runtime v4 uses a program deployment workflow involving the editor, a program archive, and runtime-side processing.

At a high level:

```text
+----------------------------------+
|         OpenPLC Editor           |
|                                  |
|  Program design and compilation  |
+----------------------------------+
                 |
                 v
+----------------------------------+
|       Program Package            |
|                                  |
|  Generated source and metadata   |
+----------------------------------+
                 |
                 v
+----------------------------------+
|        Runtime API Server        |
|                                  |
|  Upload / Validation / Handling  |
+----------------------------------+
                 |
                 v
+----------------------------------+
|        Runtime Build Process     |
|                                  |
|  Compile / Produce program module|
+----------------------------------+
                 |
                 v
+----------------------------------+
|         PLC Runtime Core         |
|                                  |
|  Load and execute application    |
+----------------------------------+
```

The editor performs program preparation and generates the files required by the runtime. The editor then packages the relevant generated files for transfer. The runtime accepts the package through its management interface and processes the supplied files to produce the executable application module.

This division of responsibilities is important: the engineering environment, program transfer mechanism, runtime-side compilation, and execution core represent different stages of the overall application lifecycle.

The integrity of the deployed application depends on more than the correctness of the control logic itself. It also depends on how the program is prepared, transferred, validated, compiled, and loaded.

However, the existence of these stages does not establish that a particular stage is vulnerable or adequately protected. Those conclusions require examining the implementation and observing its behavior.

The detailed compilation pipeline and program-loading behavior belong to later investigations, where they can be examined without turning this primer into a full toolchain audit.

Reference: [OpenPLC Runtime v4 compilation flow](https://github.com/Autonomy-Logic/openplc-runtime/blob/main/docs/COMPILATION_FLOW.md).

# 7. Input / Output Architecture

The control application must interact with process inputs and outputs. In a software PLC, this interaction is mediated by the runtime and the I/O facilities available on the host platform.

OpenPLC Runtime v4 provides a plugin system for extending its I/O functionality. This allows platform-specific or application-specific I/O implementations to be integrated without requiring every supported interface to be embedded directly into the central execution logic.

A conceptual representation is:

```text
          PLC Control Application
                     |
                     v
              Runtime Core
                     |
                     v
              I/O Interface
                     |
                     v
             Driver / Plugin
                     |
                     v
        Device, Network or Simulation
```

The diagram represents a functional relationship, not a verified execution path for every plugin.

The I/O implementation determines how logical values are connected to the relevant external interface. Depending on the deployment, those interfaces may represent physical devices, network-connected equipment, or simulated process values.

This matters because the application's logical state and the external process state are not necessarily identical at every instant. For example, an output value calculated by the control application does not, by itself, prove that the corresponding external device received or applied that value. The result depends on the execution path, the I/O implementation, and the state of the interface or device.

The plugin architecture also introduces additional components into the runtime environment. Their loading, configuration, privileges, and interaction with the execution core may influence the overall security properties of the system. The actual plugin configuration and the runtime's interaction with device and operating-system interfaces must be established through the later hardware and kernel-interface investigation.

# 8. The Host Operating System and Runtime Environment

OpenPLC Runtime v4 executes on a host operating system that supplies the resources and facilities required for operation.

The host provides processor time, memory, filesystem access, networking, process management, and access to supported device interfaces. The runtime's effective capabilities are therefore influenced by both its own implementation and the configuration of the environment in which it runs.

A simplified representation is:

```text
+------------------------------------------+
|             OpenPLC Runtime              |
|                                          |
|      Management Service / PLC Core       |
+------------------------------------------+
                     |
                     v
+------------------------------------------+
|            Host Operating System         |
|                                          |
|  Process Management / Scheduling         |
|  Memory / Filesystem / Networking        |
|  Permissions / Capabilities / Devices    |
+------------------------------------------+
                     |
                     v
+------------------------------------------+
|              Host Resources              |
|                                          |
|        CPU / RAM / Storage / I/O         |
+------------------------------------------+
```

The operating system influences which operations the runtime can perform and how its processes are scheduled and isolated.

For example, process privileges determine which protected operations may be permitted. Filesystem permissions influence access to configuration and program files. Scheduling policies influence processor allocation, while device permissions affect access to hardware interfaces.

The v4 project documentation identifies real-time scheduling and certain startup requirements as reasons for elevated privileges in supported deployment configurations. The exact privileges required and the manner in which they are granted must be verified for the build and deployment used in this research.

The runtime may also be deployed inside a container or virtual machine. Such an environment introduces additional resource and isolation boundaries, but those boundaries depend on the configuration of the container, hypervisor, and underlying host.

The important architectural point is that the runtime's security boundary does not end at its own application code. It extends into the operating-system facilities and deployment controls that determine the resources and operations available to it.

The detailed examination of capabilities, device access, memory mappings, scheduling, and isolation is reserved for the relevant investigation phases.

# 9. Architectural Trust Boundaries

A trust boundary separates components or environments whose access rights, responsibilities, or security properties cannot simply be assumed to be equivalent.

For OpenPLC Runtime v4, the architecture introduces several boundaries worth distinguishing:

```text
       OpenPLC Editor / API Client
                    |
                    | External interface
                    v
+------------------------------------------+
|             REST API Server              |
|                                          |
|  Authentication / Management / Debugging |
+------------------------------------------+
                    |
                    | Local IPC
                    v
+------------------------------------------+
|              PLC Runtime Core            |
|                                          |
|        Application Execution / State     |
+------------------------------------------+
                    |
                    | I/O interface
                    v
+------------------------------------------+
|          Plugins / Host Interfaces       |
+------------------------------------------+
                    |
                    v
             External Process
```

This model separates external client access, management, execution, and process I/O. It does not imply that each boundary is enforced through a dedicated security mechanism. 

The difference between a functional boundary and an enforced security boundary is fundamental. Two components may perform different functions while sharing privileges or access to sensitive resources. Conversely, components may be separated by process boundaries and communicate through a mechanism subject to operating-system access controls.

The security significance of each boundary depends on how it is implemented.

# 10. Security Significance of the Architecture

The architecture of a software PLC influences the consequences of a security failure.

In a conventional information system, unauthorized access may affect application data or service availability. In an industrial control environment, access to the control application, runtime state, or process I/O may also affect the behavior of the system being controlled.

The consequences depend on the application, deployment, connected equipment, and protections actually enforced.

Several broad security concerns follow from the architecture described in this primer.

✔ **Management integrity:** Unauthorized management operations may affect runtime configuration, program deployment, or operational state.

✔ **Execution integrity:** Interference with the execution core may affect whether the intended control application executes correctly.

✔ **Application integrity:** Changes to the deployed program may alter the decisions made by the controller.

✔ **Internal communication security:** Weak restrictions on IPC channels may expose commands, state transitions, or runtime information to unauthorized local processes.

✔ **Process-state integrity:** Unauthorized changes to logical input or output values may cause the runtime's view of the process to diverge from the actual process state.

✔ **Availability:** Failures affecting the API service, execution core, host resources, or I/O path may prevent the controller from performing its intended function.

✔ **Isolation:** Inadequate restrictions between the runtime and its surrounding environment may expose resources beyond those required for normal operation.

These concerns are architectural categories.

The presence of TLS, JWT authentication, process separation, or operating-system access controls does not independently establish the security of the overall system. Their effectiveness depends on implementation, configuration, and the boundaries they actually protect.

The purpose of the subsequent investigations is to determine how these mechanisms operate in the target and what the evidence supports.

# Security Characteristics

The architectural baseline established in this primer can be summarized as follows:

- **OpenPLC Runtime v4 is a software-based PLC runtime** that executes control applications on a supported host platform.
- **The runtime uses a dual-process architecture**, separating the REST API server from the C/C++ PLC execution core.
- **External management is API-driven**, with HTTPS, JWT-based authentication, and a WebSocket debugging interface documented by the project.
- **Internal communication uses Unix domain sockets**, separating local management-to-runtime communication from the external network interface.
- **Program deployment involves distinct preparation, transfer, processing, and execution stages**, each with its own architectural responsibilities.
- **The runtime supports an extensible I/O plugin system**, connecting control logic to platform-specific or simulated interfaces.
- **The host operating system is part of the effective security boundary**, influencing process privileges, scheduling, resource access, and device interaction.
- **Functional separation does not automatically establish complete security isolation.** The effectiveness of process boundaries, authentication, IPC permissions, and host controls requires verification.
- **The security implications depend on the deployed version and configuration.** Architectural descriptions establish relevant questions but do not, by themselves, demonstrate vulnerabilities or effective safeguards.

This primer establishes the architectural vocabulary and baseline for the OpenPLC Runtime v4 research series. The subsequent investigations will move from this model to the actual implementation, using source examination, controlled laboratory experiments, and reproducible evidence to establish how the runtime behaves.

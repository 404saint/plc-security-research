# Phase 2: IPC & Communication Channels

* **Target Runtime:** OpenPLC v4 (`openplc-v4-lab` container)
* **Research Area:** Inter-Process Communication (IPC)
* **Primary Mechanisms:** Unix domain stream sockets
* **Observed Components:** Webserver, PLC runtime, EtherDOG
* **Objective:** Map the observed IPC endpoints, identify their communication roles, and document message handling and filesystem-level access characteristics.

---

## Executive Summary

Phase 2 examined the inter-process communication architecture of the OpenPLC v4 runtime using live container inspection and source-code review.

Three Unix domain socket endpoints were identified under `/run/runtime`:

- `/run/runtime/plc_runtime.socket` for PLC command/control communication.
- `/run/runtime/log_runtime.socket` for log communication.
- `/run/runtime/etherdog.socket` for EtherDOG control.

Inspection of the webserver's Python implementation established how the PLC client connects to its Unix stream socket, encodes outgoing messages, receives text responses, and handles newline-oriented message boundaries. The logging server implementation showed a separate Unix stream socket that accepts client connections and processes incoming data line by line.

The native PLC socket header defines command-buffer, response-size, and client-count constants. The native logging header defines the logging endpoint and exposes logging functions for multiple severity levels.

Runtime filesystem inspection also established that the PLC and logging socket entries had mode `0755`, while the EtherDOG control socket had mode `0600`. The EtherDOG protocol documentation describes peer-UID checks for its control channel.

The resulting architecture separates PLC command/control, log delivery, and EtherDOG control into distinct IPC endpoints. The observed source code and runtime metadata provide a concrete baseline for understanding the communication paths and their filesystem-level access characteristics.

# 1. Runtime IPC Architecture

The runtime inspection identified three primary Unix domain socket paths.

| Endpoint | Identified role | Observed mode | Owner |
|---|---|---|---|
| `/run/runtime/plc_runtime.socket` | PLC command/control | `0755` | `root:root` |
| `/run/runtime/log_runtime.socket` | Log communication | `0755` | `root:root` |
| `/run/runtime/etherdog.socket` | EtherDOG control | `0600` | `root:root` |

The socket types appeared as `srwxr-xr-x` for the PLC and logging endpoints and `srw-------` for the EtherDOG endpoint.

The communication architecture can be represented as:

```text
                 OpenPLC v4 Runtime
                          │
             ┌────────────┴────────────┐
             │                         │
             ▼                         ▼
         Webserver                 PLC Runtime
             │                         │
             │                         │
             ├── PLC command channel ──┤
             │   plc_runtime.socket    │
             │                         │
             └── Log channel ──────────┤
                 log_runtime.socket    │
                                       │
             EtherDOG Control          │
             etherdog.socket           │
```

The diagram summarizes the identified endpoints and their documented or source-supported roles. It does not imply that every connection direction or runtime message was independently traced.

# 2. PLC Command/Control Channel

The PLC command channel connects the webserver-side client implementation to the native PLC socket interface.

**Endpoint:** `/run/runtime/plc_runtime.socket`

## 2.1 Webserver Client

The implementation in `webserver/unixclient.py` defines the `SyncUnixClient` class.

The client creates its socket using:

```python
socket.socket(
    socket.AF_UNIX,
    socket.SOCK_STREAM
)
```

It then connects to the configured Unix socket path.

Outgoing messages are encoded from strings and transmitted using `sendall()`:

```python
data = msg.encode()
self.sock.sendall(data)
```

The response-handling implementation receives data in chunks, accumulates the bytes, and looks for a newline to identify the end of a response. The accumulated response is decoded as UTF-8 and stripped of surrounding whitespace.

The client also implements:

- Socket timeouts for blocking operations.
- A mutex to coordinate send and receive operations.
- Connection cleanup before reconnecting.
- A bounded receive buffer.

## 2.2 Native Interface Definitions

The native header `core/src/plc_app/unix_socket.h` defines the same socket path and declares the functions used to set up and operate the native socket interface.

Its constants are:

| Constant | Value | Defined purpose |
|---|---:|---|
| `COMMAND_BUFFER_SIZE` | `8192` | Command buffer size |
| `MAX_RESPONSE_SIZE` | `65536` | Maximum response size |
| `MAX_CLIENTS` | `1` | Maximum client count |

The header also declares `setup_unix_socket()`, `close_unix_socket()`, and `unix_socket_thread()`.

## 2.3 Message Handling Model

The inspected client implementation establishes the following message-handling sequence:

```text
Webserver
    │
    ▼
String Message
    │
    ▼
UTF-8 Encoding
    │
    ▼
Unix Stream Socket
    │
    ▼
PLC Runtime Interface
    │
    ▼
Response Bytes
    │
    ▼
UTF-8 Decoding
    │
    ▼
Text Response
```

The client therefore uses a text-oriented interface over a Unix domain stream socket. The native header's buffer constants provide the corresponding interface limits defined by the native implementation.

# 3. Logging Channel

The logging channel uses a separate Unix domain stream socket.

**Endpoint:** `/run/runtime/log_runtime.socket`

## 3.1 Server Implementation

The implementation in `webserver/unixserver.py` defines the `UnixLogServer` class.

During initialization, the server uses the logging socket path as its default endpoint. Its startup routine creates an `AF_UNIX` / `SOCK_STREAM` socket, binds it to the path, and starts listening for incoming connections.

Accepted clients are added to a client list and handled by separate threads.

The client handler reads each connection as a text stream:

```python
with client_sock.makefile('r') as f:
    for line in f:
        parser.parse_and_log(line)
```

Each incoming line is passed to `LogParser.parse_and_log()`.

The server also maintains client state and includes a shutdown routine that closes the server socket, closes connected clients, and attempts to remove the socket path.

## 3.2 Native Logging Interface

The header `core/src/plc_app/utils/log.h` defines:

```c
#define LOG_SOCKET_PATH "/run/runtime/log_runtime.socket"
```

It declares functions for four logging levels:

| Function | Logging level |
|---|---|
| `log_debug()` | Debug |
| `log_info()` | Informational |
| `log_warn()` | Warning |
| `log_error()` | Error |

The interface also declares `log_emergency()` for emergency messages.

## 3.3 Logging Flow

The observed server-side processing can be summarized as:

```text
Incoming Unix Socket Connection
              │
              ▼
         Client Stream
              │
              ▼
        Read Line by Line
              │
              ▼
 LogParser.parse_and_log()
              │
              ▼
       Runtime Log Handling
```

The Python implementation establishes that the log server consumes incoming text line by line. The native header establishes the corresponding logging interface and endpoint.

The logging channel is separate from the identified PLC command/control socket.

# 4. EtherDOG Control Channel

The EtherDOG control interface uses its own Unix domain socket path.

**Endpoint:** `/run/runtime/etherdog.socket`

## 4.1 Runtime Filesystem Evidence

The socket entry was observed with the following attributes:

| Attribute | Observed value |
|---|---|
| Socket type | Unix domain socket |
| Permission mode | `0600` |
| Owner | `root:root` |
| Path | `/run/runtime/etherdog.socket` |

The source reference `webserver/etherdog_manager.py` contains the EtherDOG control socket configuration. The inspected protocol documentation, `third_party/etherdog/docs/PROTOCOL.md`, describes the control socket as using mode `0600` and documents peer checks based on user ID.

The runtime filesystem also contained `/run/runtime/etherdog.json` with mode `0600`.

## 4.2 Access-Control Characteristics

The observed filesystem mode differs from those recorded for the PLC and logging socket entries.

```text
PLC Command Socket       0755
Logging Socket           0755
EtherDOG Control Socket  0600
```

The `0600` mode grants filesystem read/write permission to the owning user, with no permissions granted to the group or other users.

The documented peer-UID checks provide a separate access-control mechanism described by the EtherDOG protocol documentation.

These observations establish a difference in filesystem permissions and document the stated peer-identity check for EtherDOG.

# 5. Runtime Processes and Socket Descriptors

Runtime inspection identified the following processes in the container:

| PID | Process |
|---:|---|
| `1` | Python webserver |
| `21` | EtherDOG |
| `878` | PLC runtime (`plc_main`) |

All three processes were observed running as `root:root` within the container.

Inspection of `/proc/net/unix` showed socket entries associated with the identified paths. Inspection of `/proc/<pid>/fd` also showed socket descriptors belonging to the observed processes, including descriptors associated with named endpoints and descriptors without displayed pathnames.

The webserver process held an open descriptor for:

```text
/run/runtime/restapi.db
```

The database file was identified as SQLite from its file header:

```text
SQLite format 3
```

These observations establish the presence of the relevant processes, socket descriptors, and database file in the inspected runtime environment.

# 6. Filesystem-Level Access Characteristics

The runtime directory contained several files and directories with different permission modes.

| Path | Observed mode | Observed type |
|---|---|---|
| `/run/runtime/plc_runtime.socket` | `0755` | Unix socket |
| `/run/runtime/log_runtime.socket` | `0755` | Unix socket |
| `/run/runtime/etherdog.socket` | `0600` | Unix socket |
| `/run/runtime/etherdog/` | `0700` | Directory |
| `/run/runtime/etherdog.json` | `0600` | File |
| `/run/runtime/.env` | `0600` | File |
| `/run/runtime/restapi.db` | `0644` | File |

The entries were observed inside the container and owned by `root:root`.

These permission modes describe filesystem-level access attributes. They should be interpreted in the context of the container's user and filesystem environment rather than as a complete statement of host-level access.

The `.env` file was not read. Its presence, file type, ownership, and permission mode were sufficient for the filesystem inventory recorded here.

# 7. Security Characteristics

## 7.1 Separation of IPC Roles

The runtime exposes distinct Unix socket paths for PLC command/control, logging, and EtherDOG control.

```text
                    Runtime IPC
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
       PLC Control      Logging       EtherDOG
          │              │              │
          ▼              ▼              ▼
    plc_runtime       log_runtime     etherdog
       .socket          .socket        .socket
```

This separation establishes distinct IPC endpoints for different runtime responsibilities.

## 7.2 Text-Oriented Communication

The inspected webserver client encodes outgoing command messages from strings and decodes responses as UTF-8. The logging server reads incoming streams line by line.

These implementation details establish text-oriented message handling at the inspected Python interfaces.

## 7.3 Different Filesystem Permission Modes

The observed PLC and logging socket entries used mode `0755`, while the EtherDOG control socket used mode `0600`.

This is a concrete difference in the filesystem permissions applied to the three endpoints. The EtherDOG protocol documentation additionally describes peer-UID checks.

The socket mode alone does not describe every aspect of connection authorization; the finding here is the recorded difference in permissions and the documented EtherDOG access-control behavior.

## 7.4 Native Interface Limits

The native PLC socket header defines a command buffer of `8192` bytes, a maximum response size of `65536` bytes, and a maximum client count of `1`.

These definitions provide explicit interface parameters for the PLC socket implementation.

# Key Takeaways

Phase 2 documented the IPC layout of the OpenPLC v4 runtime using source inspection and live container evidence.

The runtime uses three identified Unix domain socket endpoints to separate PLC command/control, log delivery, and EtherDOG control. The inspected Python code established text-oriented message handling for the PLC client and logging server, while the native headers defined the corresponding PLC and logging interfaces.

Runtime inspection also established the process associations, socket ownership, filesystem permission modes, and presence of an SQLite database used by the webserver process.

The most important result is a concrete map of the runtime's observed IPC architecture and its filesystem-level access characteristics. These findings establish the communication endpoints and implementation details documented in this phase.

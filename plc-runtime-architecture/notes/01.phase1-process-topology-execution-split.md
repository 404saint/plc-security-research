# Phase 1: Process Topology and Execution Split

- **Target Runtime:** OpenPLC Runtime v4
- **Environment:** Isolated Docker container
- **Container:** `openplc-v4-lab`
- **Primary Executable:** `./build/plc_main`
- **Research Area:** Process topology, thread structure, and lifecycle behavior


---

## Executive Summary

This investigation examines the process topology, thread-level structure, process restart behavior, and runtime execution boundaries of OpenPLC Runtime v4 in an isolated Docker lab.

The initial process inspection identified three long-running components:

- `webserver.app`, a Python management process running as PID 1.
- `etherdog`, a separate native executable.
- `plc_main`, the PLC runtime executable.

Thread-aware inspection reported 11 threads for the Python management process, 2 for `etherdog`, and 4 for `plc_main`. One thread in the PLC runtime process appeared under the name `plc_watchdog`.

The process termination test used `SIGKILL` against `plc_main`. The logs recorded unexpected termination and a restart attempt. The replacement process initialized runtime components but failed to reach the `RUNNING` state because no `libplc_*.so` file was found in the build directory. The runtime subsequently entered the `EMPTY` state.

Additional runtime inspection established that the observed persistent processes ran as root inside the container. It also identified the filesystem entries and Unix-domain sockets used for local communication. The socket paths, permission modes, process descriptor associations, and supporting runtime files were examined in the subsequent IPC investigation.

The evidence establishes process separation, the observed thread counts, and a restart attempt that did not restore the PLC runtime to `RUNNING`. It does not establish successful recovery of PLC execution, graceful shutdown behavior, or the precise responsibilities of every thread.

## 1. Investigation Scope

## Objectives

- Identify the main runtime processes and their parent-child relationships.
- Capture thread counts and visible thread names.
- Observe runtime behavior after forced termination of `plc_main`.
- Record the execution identities of the observed processes.
- Establish a baseline for understanding runtime component boundaries.
- Separate directly observed behavior from architectural interpretation.

## Scope boundaries

This phase focuses on process topology, thread visibility, execution identity, and process lifecycle behavior. The phase establishes a successful exploit or a vulnerability merely from the presence of a process, thread, or communication endpoint.

## 2. Process Topology

## 2.1 Initial process snapshot

The following command was executed inside the running container:

```bash
docker exec -it --user root openplc-v4-lab \
  ps -eo pid,ppid,lwp,stat,cmd
```

Relevant output:

```text
PID  PPID  LWP  STAT  CMD
1    0     1    Ssl   /workdir/venvs/runtime/bin/python3 -m webserver.app
21   1     21   Sl    ./build/etherdog --control unix:/run/runtime/etherdog.socket --state-dir /run/runtime/etherdog --log-socket unix:/run/runtime/log_runtime.socket
821  1     821  Sl    ./build/plc_main
```

The command also displayed the `ps` process itself. That process was temporary and was not part of the persistent runtime topology.

## 2.2 Observations

- PID 1 runs the Python module `webserver.app`.
- PID 21 runs `./build/etherdog`.
- PID 821 runs `./build/plc_main` in the initial snapshot.
- Both `etherdog` and `plc_main` have PPID 1 in the captured output.
- The `etherdog` command line specifies a control socket, a state directory, and a log socket.
- Process identifiers varied between snapshots, so the PIDs should be understood as measurements from specific points in time.

## 2.3 Interpretation

The runtime consists of multiple processes rather than a single executable handling every responsibility.

The Python management process is PID 1 inside the container, while `etherdog` and `plc_main` appear as separate child processes. This establishes the observed process relationships but does not, by itself, establish every component's internal responsibilities or dependencies.

The socket paths visible in the `etherdog` command line identify configured local communication endpoints. Their implementation, permissions, and observed runtime associations are documented in Phase 2.

## 3. Thread-Level Structure

## 3.1 Inspection command

Thread-aware inspection was performed using:

```bash
docker exec -it --user root openplc-v4-lab \
  ps -eLo pid,ppid,nlwp,lwp,stat,comm,args
```

Relevant output:

```text
PID  PPID  NLWP  LWP  STAT  COMMAND       COMMAND
1    0     11    1    Ssl   python3       ... -m webserver.app
1    0     11    18   Ssl   python3       ... -m webserver.app
...
21   1     2     21   Sl    etherdog      ./build/etherdog ...
21   1     2     23   Sl    etherdog      ./build/etherdog ...
878  1     4     878  Sl    plc_main      ./build/plc_main
878  1     4     879  Sl    plc_main      ./build/plc_main
878  1     4     880  Sl    plc_watchdog  ./build/plc_main
878  1     4     888  Sl    plc_main      ./build/plc_main
```

The abbreviated output preserves the relevant entries. The original terminal output remains the primary evidence for the complete snapshot.

## 3.2 Observations

At the time of this inspection:

| Process | PID | Reported thread count (`NLWP`) | Notable observation |
|---|---:|---:|---|
| Python management server | 1 | 11 | Multiple LWPs belong to the same process |
| `etherdog` | 21 | 2 | Two LWPs are listed |
| PLC runtime | 878 | 4 | One LWP is named `plc_watchdog` |

These measurements are snapshot-specific. Thread counts and identifiers may change during runtime operation.

## 3.3 Interpretation

All three components were reported with multiple threads or lightweight processes by the thread-aware inspection command.

The name `plc_watchdog` suggests a watchdog-related role within the PLC runtime. The name alone does not establish what the thread monitors, how it detects failures, or what actions it performs.

Likewise, thread counts alone do not identify which threads execute the PLC scan cycle, handle communication, or coordinate state transitions. Those responsibilities cannot be established from this process listing.

## 4. Process Execution Identity

## 4.1 Observation

During the runtime and IPC inspections, the persistent processes were observed running as `root:root` inside the container.

The relevant components were:

- Python management process: PID 1
- `etherdog`: PID 21
- PLC runtime process: PID 878 in the later snapshot

## 4.2 Interpretation

The observed processes share the same effective container-level execution identity in the captured environment. The inspection does not establish whether the container's root identity maps to unrestricted root privileges on the host or whether host-side restrictions are effective.

Process identity is only one part of the security boundary. Container configuration, Linux capabilities, namespaces, filesystem mounts, and host enforcement also affect the privileges available to a process. Those properties were not established by these observations.

## 5. Process Termination and Restart Behavior

## 5.1 Test procedure

The PLC runtime process was forcibly terminated using:

```bash
docker exec -it --user root openplc-v4-lab \
  pkill -9 plc_main
```

The process list was then captured again:

```bash
docker exec -it --user root openplc-v4-lab \
  ps -eo pid,ppid,lwp,stat,cmd
```

The subsequent snapshot showed:

```text
PID  PPID  LWP  STAT  CMD
1    0     1    Ssl   /workdir/venvs/runtime/bin/python3 -m webserver.app
21   1     21   Sl    ./build/etherdog ...
878  1     878  Rl    ./build/plc_main
```

The initial snapshot showed `plc_main` as PID 821. The later snapshot showed PID 878. The logs collected during the test identify the termination and restart sequence.

## 5.2 Log evidence

Container logs were collected using:

```bash
docker logs --since 10m openplc-v4-lab
```

The logs contained the following sequence:

```text
[2026-10-19 08:59:04] [INFO] Log server stopped
[2026-10-19 08:59:04] [WARNING] PLC runtime process died unexpectedly (exit code -9)
[2026-10-19 08:59:04] [WARNING] Restarting PLC runtime...
[2026-10-19 08:59:04] [INFO] Log server started at /run/runtime/log_runtime.socket
```

Subsequent startup messages included:

```text
[2026-10-19 08:59:05] [INFO] UNIX socket server setup at /run/runtime/plc_runtime.socket
[2026-10-19 08:59:05] [INFO] PLC State: TRANSITIONING_TO_RUN
[2026-10-19 08:59:05] [ERROR] No libplc_*.so file found in ./build
[2026-10-19 08:59:05] [ERROR] Failed to find libplc file
[2026-10-19 08:59:05] [INFO] PLC State: EMPTY
[2026-10-19 08:59:05] [ERROR] State transition to RUNNING failed
```

The collected logs contained multiple instances of the unexpected-termination and restart sequence.

## 5.3 Observations

- The termination command used signal 9 (`SIGKILL`).
- The logs recorded an unexpected runtime exit with code `-9`.
- The logs explicitly recorded a restart attempt.
- The replacement process initialized runtime components and recreated the logged PLC runtime socket endpoint.
- The replacement process failed to locate a `libplc_*.so` file in `./build`.
- The runtime transitioned to `EMPTY`, and the attempt to enter `RUNNING` failed.
- The Python management process remained present in the subsequent process snapshots.
- A watchdog scheduling warning was also recorded during startup.

## 5.4 Watchdog scheduling warning

The logs included:

```text
[WARNING] Watchdog: SCHED_FIFO(99) failed: Operation not permitted
```

This establishes that the requested `SCHED_FIFO(99)` scheduling operation failed in the observed environment. It does not establish the watchdog's effective scheduling policy after the failure, its overall effectiveness, or a resulting security vulnerability.

## 5.5 Interpretation

The observed sequence is consistent with a runtime supervision mechanism detecting the death of `plc_main` and attempting to restart it.

The replacement process's initialization messages establish that startup activity occurred after termination. However, the missing PLC shared library prevented the observed transition to `RUNNING`.

**A process restart is not equivalent to successful recovery of PLC execution.** The evidence supports a restart attempt followed by a failed transition to the running state.

The available evidence does not establish whether the missing library resulted from the test, the initial lab configuration, or another condition. Because the test used `SIGKILL`, it also does not establish how the runtime behaves during graceful shutdown or whether normal cleanup and state-preservation procedures complete successfully.

## 6. Runtime Filesystem and IPC Context

The subsequent IPC investigation examined runtime files and socket endpoints under `/run/runtime`. These findings provide additional context for the process topology documented in this phase.

## 6.1 Observed runtime entries

| Entry | Observed mode | Ownership | Observation |
|---|---|---|---|
| `/run/runtime/etherdog.socket` | `0600` | `root:root` | Unix-domain socket |
| `/run/runtime/log_runtime.socket` | `0755` | `root:root` | Unix-domain socket |
| `/run/runtime/plc_runtime.socket` | `0755` | `root:root` | Unix-domain socket |
| `/run/runtime/etherdog/` | `0700` | `root:root` | Directory |
| `/run/runtime/etherdog.json` | `0600` | `root:root` | Runtime configuration file |
| `/run/runtime/.env` | `0600` | `root:root` | File present; contents not read |
| `/run/runtime/restapi.db` | `0644` | `root:root` | SQLite database file |

The mode values represent the filesystem permissions observed during inspection. They are not, by themselves, proof of successful or unsuccessful access by a particular client.

In particular, the `0755` modes on the two sockets do not establish that arbitrary local users can connect. Unix-domain socket connection permissions, directory traversal, process identity, and application-level checks all matter.

## 6.2 Process socket descriptors

Inspection of `/proc/net/unix` and `/proc/<pid>/fd` identified socket descriptors associated with the Python management process, `etherdog`, and `plc_main`.

The observed descriptor and inode associations are consistent with these processes participating in the runtime's local socket-based communication architecture. The snapshot does not independently establish every socket's direction, connected peer, or message sequence.

The IPC investigation documents the identified endpoints and their observed filesystem characteristics in detail.

## 6.3 Runtime database

The first 16 bytes of `/run/runtime/restapi.db` were inspected:

```bash
od -An -N16 -tc /run/runtime/restapi.db
```

The output contained the `SQLite format 3` header, identifying the file as an SQLite database.

This confirms the file format but does not establish the database schema, sensitivity of stored records, or whether its permissions create an exploitable condition.

## 7. Security and Reliability Significance

The findings establish several architectural characteristics relevant to runtime security analysis:

1. **Process separation:** The management server, PLC runtime, and `etherdog` appear as separate processes. This provides distinct process boundaries for examining communication and privilege relationships.
2. **Shared execution identity:** The persistent processes were observed running as root inside the container. This is a relevant architectural property, but host-level privilege implications depend on the container configuration.
3. **Threaded execution:** The processes contain multiple threads, including a PLC runtime thread named `plc_watchdog`. Thread names and counts do not establish the implementation of their responsibilities.
4. **Restart behavior:** Forced termination triggered a logged restart attempt, but the replacement process did not return to `RUNNING`.
5. **Scheduling constraints:** The requested `SCHED_FIFO(99)` scheduling operation failed with `Operation not permitted`. The operational consequences remain unestablished.
6. **Local IPC architecture:** The processes use Unix-domain socket endpoints. Their paths, modes, and observed process associations are documented in Phase 2.
7. **Runtime filesystem artifacts:** The inspection identified socket files, a runtime configuration file, an environment file, and an SQLite database. Their presence and modes are observations, not vulnerability findings by themselves.

These results establish a baseline for understanding the runtime's process boundaries and observed failure behavior. They do not independently demonstrate a security vulnerability.

## 8. Key Takeaways

- OpenPLC Runtime v4 runs as multiple processes in the tested container.
- The captured thread-aware snapshot reported 11 threads for the Python management server, 2 for `etherdog`, and 4 for `plc_main`.
- A thread named `plc_watchdog` appeared in the PLC runtime process listing.
- The observed persistent processes ran as `root:root` inside the container.
- Forced termination of `plc_main` triggered a logged restart attempt.
- The replacement process failed to reach `RUNNING` because no `libplc_*.so` file was found in the build directory.
- The requested watchdog scheduling operation failed with `Operation not permitted`.
- Runtime inspection identified Unix-domain sockets and other filesystem artifacts, with their paths and observed permissions documented in Phase 2.
- The evidence does not establish successful PLC execution recovery, graceful shutdown behavior, or the precise responsibilities of every thread.

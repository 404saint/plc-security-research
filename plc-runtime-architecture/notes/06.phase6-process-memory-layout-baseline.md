# Phase 6: Process Memory Layout Baseline

- **Domain:** OpenPLC Runtime v4
- **Focus:** Virtual memory mappings and memory access permissions
- **Target process:** `plc_main` (PID 878)
- **Environment:** `openplc-v4-lab` Docker container
- **Status:** Baseline captured

---

## Executive Summary

This investigation establishes a read-only baseline of the virtual memory layout of the OpenPLC Runtime v4 `plc_main` process before user logic is deployed.

The captured `/proc/878/maps` output shows the main executable mapped into separate read-only, executable, and writable regions. It also identifies a heap, anonymous memory mappings, thread-stack-related memory regions, and multiple loaded shared objects, including EtherCAT and S7comm plugins.

The main executable has separate mappings with read-and-execute (`r-xp`) and read-and-write (`rw-p`) permissions. The inspected shared libraries similarly use separate executable and writable mappings. No single permission pattern applies to every mapping: anonymous regions and stack memory have their own permissions, and some regions are marked inaccessible (`---p`).

This snapshot records the layout at one point in the runtime lifecycle. It does not identify the contents of individual allocations or prove where specific PLC operational structures reside. No memory was modified, and no injection or integrity-manipulation testing was performed.

## 1. Collection Method

Command:

```bash
docker exec -it --user root openplc-v4-lab sh -c '
for pid in $(pgrep plc_main); do
  echo "=== Memory Map for plc_main (PID $pid) ==="
  cat /proc/$pid/maps
done'
```

The output was collected from `/proc/[pid]/maps`, which reports the virtual address ranges mapped into a process, their permissions, file offsets, mapping identifiers, and associated file paths where available.

The captured process was PID `878`. The output is a snapshot and may change as the process allocates memory, loads or unloads libraries, creates threads, or changes runtime state.

## 2. Main Executable Memory Regions

The main executable appears at several addresses under `/workdir/build/plc_main`.

| Virtual address range | Permissions | File offset | Observation |
|---|---|---:|---|
| `5a8badf99000-5a8badfa0000` | `r--p` | `0x00000` | Read-only mapping |
| `5a8badfa0000-5a8badfaf000` | `r-xp` | `0x07000` | Readable and executable mapping |
| `5a8badfaf000-5a8badfb7000` | `r--p` | `0x16000` | Read-only mapping |
| `5a8badfb7000-5a8badfb8000` | `r--p` | `0x1d000` | Additional read-only mapping |
| `5a8badfb8000-5a8badfb9000` | `rw-p` | `0x1e000` | Readable and writable mapping |

These entries show that the executable is not mapped as one uniformly readable, writable, and executable region. Its executable mapping is separate from its writable mapping in this snapshot.

The final writable mapping is consistent with writable data associated with the executable's mapped image. However, `/proc/[pid]/maps` alone does not identify individual `.data` or `.bss` symbols or establish which variables occupy the region.

The executable's file-backed mapping is followed by an anonymous writable region:

```text
5a8badfb9000-5a8bae370000 rw-p 00000000 00:00 0
```

This region is not labelled as a named mapping in the captured output. Its specific allocation purpose cannot be determined from the mapping entry alone.

## 3. Heap and Anonymous Memory

## 3.1 Heap

The process has a mapping explicitly labelled `[heap]`:

```text
5a8bddc7b000-5a8bde6ce000 rw-p 00000000 00:00 0 [heap]
```

The heap is readable and writable. It is commonly used for dynamic allocation, but this mapping does not reveal which runtime objects or PLC-related structures are stored there.

## 3.2 Anonymous mappings

The map contains numerous anonymous memory regions. Examples include:

```text
753a50000000-753a50021000 rw-p 00000000 00:00 0
753a50021000-753a54000000 ---p 00000000 00:00 0
753a568bd000-753a570bd000 rw-p 00000000 00:00 0
753a570bd000-753a57925000 rw-p 00000000 00:00 0
```

These entries show both writable anonymous mappings and a region without read, write, or execute permissions.

Anonymous mappings may support runtime allocations, thread stacks, allocator arenas, or other process facilities. Their precise purposes cannot be assigned reliably from these entries alone.

The inaccessible (`---p`) region is not readable, writable, or executable under the permissions shown in this snapshot. Its presence alone does not establish why the region was reserved.

## 4. Loaded Shared Objects and Plugins

The memory map confirms that multiple shared objects are loaded into the PLC runtime process.

## 4.1 Industrial protocol plugins

| Loaded object | Observed mapping permissions |
|---|---|
| `/workdir/build/plugins/libethercat_plugin.so` | Read-only, executable, and writable regions |
| `/workdir/build/plugins/libs7comm_plugin.so` | Read-only, executable, and writable regions |

For the EtherCAT plugin, the map includes an executable region:

```text
753a585a1000-753a585ad000 r-xp 00003000 00:90 3423796 /workdir/build/plugins/libethercat_plugin.so
```

It also includes a separate writable region:

```text
753a585b1000-753a585b2000 rw-p 00012000 00:90 3423796 /workdir/build/plugins/libethercat_plugin.so
```

The S7comm plugin has a similar separation between executable and writable mappings.

These entries establish that both plugin shared objects are mapped into the inspected process. They do not, by themselves, prove which protocol functions are active or whether either plugin is currently processing traffic.

## 4.2 Additional loaded libraries

The map also includes libraries and extension modules from the Python OPC UA virtual environment and system library directories. Examples include:

- `libcrypto.so.3` and `libssl.so.3`
- `libc.so.6` and `libm.so.6`
- `libstdc++.so.6`
- `libpython3.11.so.1.0`

Their presence indicates that these shared objects are mapped into the process address space. Their presence does not establish that every exported function is used during normal runtime operation.

## 5. Memory Protection Baseline

The permission flags in `/proc/[pid]/maps` provide a snapshot of access permissions for each virtual memory region.

| Flag | Meaning |
|---|---|
| `r` | Read permission |
| `w` | Write permission |
| `x` | Execute permission |
| `-` | Permission absent |
| `p` | Private mapping |

Observed patterns include:

- **`r--p`:** Read-only private mappings, used for several executable and library regions.
- **`r-xp`:** Readable and executable private mappings, observed for the main executable and shared libraries.
- **`rw-p`:** Readable and writable private mappings, observed for writable executable/library regions, the heap, and anonymous memory.
- **`---p`:** Regions with no read, write, or execute permissions in the captured snapshot.

The main executable and inspected protocol plugins have separate executable and writable mappings rather than a single mapping that is both writable and executable.

This is a descriptive observation of the current mapping permissions, not a complete evaluation of the process's memory protection or security posture. The snapshot does not establish whether mappings change during operation or whether other protection mechanisms are enabled.

## 6. Volatility and Baseline Scope

The memory layout contains several categories of state:

- **Executable image:** File-backed mappings associated with `plc_main`.
- **Shared libraries:** File-backed mappings for protocol plugins, runtime libraries, and Python extension modules.
- **Heap:** A named writable region commonly used for dynamic allocation.
- **Anonymous memory:** Additional mapped regions whose individual purposes are not identified by the listing.
- **Stack:** A mapping labelled `[stack]` near the top of the process address space.
- **Kernel-provided virtual mappings:** Entries such as `[vvar]`, `[vvar_vclock]`, `[vdso]`, and `[vsyscall]`.

The stack entry observed was:

```text
7fffa043f000-7fffa0460000 rw-p 00000000 00:00 0 [stack]
```

This is the mapping explicitly labelled `[stack]` in the captured output. The process may also use additional thread stacks that are represented as anonymous mappings, so the labelled entry should not be treated as a complete inventory of every thread's stack.

This baseline does not locate specific PLC variables, runtime execution structures, or user-logic state within the mapped regions. Those details require separate evidence and are outside the scope of this initial mapping inspection.

## Key Takeaways

- The `plc_main` executable is mapped into separate read-only, executable, and writable regions.
- A named writable heap and multiple anonymous memory regions are present.
- The captured layout includes read-only, executable, writable, and inaccessible memory mappings.
- `libethercat_plugin.so` and `libs7comm_plugin.so` are mapped into the process address space.
- Additional system libraries and Python extension modules are also loaded.
- A mapping labelled `[stack]` is visible, but the output does not provide a complete thread-stack inventory.
- The map provides a baseline of virtual address ranges and permissions, not the contents or exact locations of individual PLC operational structures.
- The inspection was read-only and did not alter process memory or runtime state.

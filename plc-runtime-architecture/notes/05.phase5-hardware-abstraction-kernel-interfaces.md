# Phase 5: Hardware Abstraction & Kernel Interfaces

- **Domain:** OpenPLC Runtime v4
- **Focus:** Device access, Linux capabilities, and I/O abstraction
- **Environment:** `openplc-v4-lab` Docker container
- **Status:** Initial inspection complete

---

## Executive Summary

This investigation examines the Linux interfaces and privileges available to OpenPLC Runtime v4, with a focus on how the software runtime may interact with physical or simulated I/O.

The inspected PLC runtime process (PID 878) has a nonempty Linux capability set that includes `CAP_NET_RAW` but excludes `CAP_SYS_RAWIO`. The captured `/dev` listing contains standard device nodes and pseudo-filesystem entries, with no obvious GPIO-, SPI-, or I²C-specific device nodes.

Process file descriptor inspection identified three socket descriptors held by `plc_main`, along with standard input, output, and error descriptors. Cross-process comparison revealed shared output pipe inodes between the PLC runtime and the Python management process. The management process also holds an open descriptor for `/run/runtime/restapi.db`. These findings provide evidence of process communication and resource use, but do not establish which interfaces implement PLC field I/O.



## 1. Linux Capability Inspection

## 1.1 Management process

Command:

```bash
docker exec -it --user root openplc-v4-lab getpcaps 1
```

Observed output:

```text
1: cap_chown,cap_dac_override,cap_fowner,cap_fsetid,
cap_kill,cap_setgid,cap_setuid,cap_setpcap,
cap_net_bind_service,cap_net_raw,cap_sys_chroot,
cap_mknod,cap_audit_write,cap_setfcap=ep
```

PID 1 is the Python management process identified during Phase 1. Its reported capabilities include privileges related to file ownership, selected permission overrides, process signaling, user and group identity changes, device-node creation, and raw network socket operations.

`CAP_SYS_RAWIO` is not present in the reported capability list.

## 1.2 PLC runtime process

Command:

```bash
docker exec -it --user root openplc-v4-lab sh -c '
for pid in $(pgrep plc_main); do
  echo "PID $pid:"
  cat /proc/$pid/status | grep Cap
done'
```

Observed output:

```text
PID 878:
CapInh: 0000000000000000
CapPrm: 00000000a80425fb
CapEff: 00000000a80425fb
CapBnd: 00000000a80425fb
CapAmb: 0000000000000000
```

The fields describe different parts of the process capability state:

- **`CapInh`:** Capabilities in the inheritable set.
- **`CapPrm`:** Capabilities the process is permitted to exercise.
- **`CapEff`:** Capabilities active for applicable permission checks.
- **`CapBnd`:** Bounding set limiting capabilities available through relevant privilege transitions.
- **`CapAmb`:** Ambient capabilities.

The permitted, effective, and bounding masks are identical in this snapshot. The mask `0xa80425fb` decodes to the same capability set reported for PID 1, including `CAP_NET_RAW` and excluding `CAP_SYS_RAWIO`.

**Finding:** The observed PLC process does not have `CAP_SYS_RAWIO` in its permitted, effective, or bounding sets.

This does not establish that all hardware I/O is impossible. Linux provides multiple ways for applications to interact with devices, and the required permissions depend on the interface, device permissions, namespace configuration, mounts, and other restrictions.

The processes were previously observed running as `root:root` inside the container. Root identity inside a container is not equivalent to unrestricted privilege over the host.

## 3. Process File Descriptor Inspection

The file descriptors of the PLC runtime, Python management process, and EtherDOG were compared to identify visible resource use and potential communication relationships.

## 3.1 PLC runtime: PID 878

The PLC runtime exposed these descriptors:

| FD | Target | Observation |
|---:|---|---|
| `0` | `/dev/null` | Standard input |
| `1` | `pipe:[178781]` | Standard output connected to a pipe |
| `2` | `pipe:[178782]` | Standard error connected to a pipe |
| `3` | `socket:[227172]` | Socket descriptor |
| `4` | `socket:[230275]` | Socket descriptor |
| `5` | `socket:[222778]` | Socket descriptor |

No descriptor in this snapshot points directly to an obvious hardware device node.

This does not prove that the runtime never opens device files. The listing captures descriptors open at a particular moment, and descriptor use can change during execution.

## 3.2 Management process: PID 1

The management process exposed the following relevant descriptors:

| FD | Target | Observation |
|---:|---|---|
| `1` | `pipe:[178781]` | Shared pipe inode with PLC runtime FD 1 |
| `2` | `pipe:[178782]` | Shared pipe inode with PLC runtime FD 2 |
| `9` | `socket:[178901]` | Matches the UDP socket inode observed in Phase 3 |
| `10` | `/run/runtime/restapi.db` | Open database file descriptor |
| `11` | `socket:[179352]` | Matches the TCP listener inode observed in Phase 3 |
| `3`, `5`, `6`, `14` | Socket inodes | Additional socket descriptors |

The shared pipe inodes provide evidence that the management process and PLC runtime have corresponding descriptors referencing the same pipe objects. This is consistent with connected process output streams, but the descriptor listing alone does not establish the full logging or supervision design.

The database descriptor confirms that `/run/runtime/restapi.db` is open in the management process at the time of inspection. It does not establish which database records are present or what operations are performed against them.

The TCP and UDP descriptor correlations are consistent with Phase 3, where the management process was observed listening on TCP port 8443 and holding a UDP socket on port 33333.

## 3.3 EtherDOG: PID 21

The listing does not identify the socket peers or prove which application-level messages travel through them.

## 4. Unix-Domain Socket Correlation

The PLC runtime's socket inodes were compared with `/proc/net/unix`.

Relevant entries included:

```text
Inode    Path
230275   /run/runtime/plc_runtime.socket
222778   /run/runtime/plc_runtime.socket
227172   [unnamed Unix-domain socket]
```

The two entries associated with `/run/runtime/plc_runtime.socket` match the inodes referenced by PLC runtime descriptors 4 and 5. Descriptor 3 matches an unnamed Unix-domain socket entry.

The table also contained entries associated with:

- `/run/runtime/log_runtime.socket`
- `/run/runtime/etherdog.socket`

These paths were identified during Phase 2. Their presence in the system socket table does not mean that `plc_main` directly uses every listed endpoint. The matching inodes establish socket associations, but do not independently reveal peer identity, communication direction, message contents, or the function of each connection.

## Interpretation

The evidence supports the conclusion that the PLC runtime uses Unix-domain sockets as part of its local communication environment. It does not demonstrate that these sockets directly carry physical or simulated field I/O. The unnamed socket remains unidentified at the application level.

## 5. Hardware Abstraction and I/O Boundary

The inspection has established three relevant facts:

1. The observed PLC process does not have `CAP_SYS_RAWIO` in its capability sets.
2. The captured `/dev` listing does not show obvious hardware-specific I/O device nodes.
3. The PLC runtime holds multiple socket descriptors, including descriptors associated with its runtime IPC path.

These facts describe the runtime's observed privilege and communication context. They do not yet reveal how PLC variables are mapped to physical or simulated inputs and outputs.

Possible I/O mechanisms include device interfaces, software-defined backends, files, shared memory, plugins, or network communication. The current evidence does not establish which of these mechanisms the inspected runtime actually uses.

The socket findings from this phase and the listener findings from Phase 3 must also remain distinct: the existence of a communication channel does not prove that it carries field I/O.

**The I/O abstraction boundary remains unconfirmed.** Determining it would require evidence from the relevant runtime implementation or a specifically identified I/O backend.

## 6. Privilege Assessment

The evidence does not support a claim that the runtime requires unrestricted root privileges or `CAP_SYS_RAWIO` solely to perform I/O.

The observed capability set and device inventory instead establish a narrower baseline: the process has selected Linux capabilities, lacks `CAP_SYS_RAWIO`, and operates in a container whose captured device listing contains no obvious hardware-specific device nodes.

Whether any particular I/O backend requires additional privileges remains dependent on its implementation and configuration. No privilege escalation, hardware access test, or device interaction was performed during this phase.


## Key Takeaways

- The observed PLC runtime capability mask includes `CAP_NET_RAW` but excludes `CAP_SYS_RAWIO`.
- The captured `/dev` listing contains standard device nodes and pseudo-filesystem entries, with no obvious hardware-specific I/O device nodes.
- The PLC runtime holds three socket descriptors in the inspected snapshot.
- Two PLC socket descriptor inodes match entries associated with `/run/runtime/plc_runtime.socket`; the third appears as an unnamed Unix-domain socket.
- The management process and PLC runtime share corresponding standard-output and standard-error pipe inodes.
- The management process has `/run/runtime/restapi.db` open and holds descriptors matching the TCP and UDP sockets recorded in Phase 3.
- The observed communication paths establish local IPC and process resource use, but do not establish the implementation of physical or simulated PLC I/O.
- The I/O abstraction boundary and any backend-specific privilege requirements remain unconfirmed.

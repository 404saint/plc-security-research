# Phase 3: Network Listener Enumeration

- **Target Runtime:** OpenPLC Runtime v4
- **Environment:** Isolated Docker container
- **Container:** `openplc-v4-lab`
- **Research Area:** Network listener enumeration
- **Primary Tool:** `ss`
- **Objective:** Identify network-facing listening sockets and their owning processes in the baseline runtime state

---

## Executive Summary

This investigation enumerates the network-facing sockets exposed by OpenPLC Runtime v4 in the baseline state of the tested Docker container.

The socket inspection identified two entries owned by the Python management process:

- **TCP `0.0.0.0:8443`** in the `LISTEN` state.
- **UDP `0.0.0.0:33333`** in the `UNCONN` state.

Both entries were attributed to `python3`, PID 1. The output identifies file descriptors 11 and 9 for the TCP and UDP sockets, respectively.

The `0.0.0.0` binding indicates that the sockets are bound to all IPv4 local interfaces within the network namespace where they were inspected. This does not, by itself, establish reachability from outside the container or host, because Docker port publishing, routing, firewall rules, and other network controls affect external exposure.

No other network sockets were reported by this command in the captured snapshot. The inspection did not send requests, test authentication, enumerate HTTP routes, or assess application-level behavior.

## 1. Investigation Scope

## Objectives

- Enumerate network-facing TCP and UDP sockets in the baseline runtime state.
- Record each listener's protocol, local address, port, and state.
- Identify the process and file descriptor associated with each socket.
- Distinguish container-level binding from externally reachable exposure.

## Scope boundaries

This phase is limited to socket and listener enumeration.

No test requests were sent. HTTP routes, authentication controls, API behavior, protocol responses, and potential application vulnerabilities remain outside this investigation.

## 2. Enumeration Procedure

The following command was executed inside the running container:

```bash
docker exec -it --user root openplc-v4-lab ss -tulpn
```

Options used:

| Option | Purpose |
|---|---|
| `-t` | Display TCP sockets |
| `-u` | Display UDP sockets |
| `-l` | Display listening sockets |
| `-p` | Display associated process information |
| `-n` | Display numeric addresses and ports |

The command was executed as root inside the container to make process ownership information available to the inspection.

## 4. TCP Listener: Port 8443

## Observations

- The socket uses TCP.
- The socket is in the `LISTEN` state.
- The local binding is `0.0.0.0:8443`.
- The socket is associated with `python3`, PID 1, file descriptor 11.
- The reported send queue limit is 128.

## Interpretation

The output establishes that the Python management process owns a TCP listening socket on port 8443, bound to all IPv4 interfaces in the container's network namespace.

The port number alone does not establish the application protocol, the use of TLS, or the purpose of the service. Those details are not inferred from the socket listing. The listener's binding is relevant to exposure analysis, but external accessibility depends on the surrounding container and host networking configuration.

## 5. UDP Socket: Port 33333

## Observations

- The socket uses UDP.
- The reported state is `UNCONN`.
- The local binding is `0.0.0.0:33333`.
- The socket is associated with `python3`, PID 1, file descriptor 9.

## Interpretation

The output establishes that the Python management process owns a UDP socket bound to port 33333 on all IPv4 interfaces in the container's network namespace.

Unlike TCP, UDP does not establish a connection before exchanging datagrams. The `UNCONN` state is consistent with a UDP socket that is not connected to a specific peer. The output does not identify the application protocol, the purpose of the socket, whether datagrams are accepted from external sources, or how received data is handled.

## 6. Binding and Exposure Characteristics

The two observed sockets use wildcard IPv4 bindings rather than explicit loopback addresses.

| Characteristic | TCP 8443 | UDP 33333 |
|---|---|---|
| IPv4 wildcard binding | Observed | Observed |
| Restricted to loopback by binding | No | No |
| Associated process identified | Yes | Yes |
| External reachability established | No | No |
| Application protocol identified | No | No |

A wildcard binding means the service is not restricted to `127.0.0.1` by its local bind address. It does not prove that the service is reachable from the host LAN or the public internet.

External reachability depends on factors including:

- Docker port publishing and network mode.
- Host firewall and forwarding rules.
- Container network configuration.
- Routing and upstream network controls.

The listener inventory therefore documents the runtime's local network binding, not a confirmed externally accessible attack surface.

## 7. Default Exposure Assessment

The captured baseline contains two network-facing socket entries owned by the Python management process.

The output does not show a separate Modbus TCP listener in this snapshot. This should be recorded as **not observed**, rather than evidence that Modbus TCP is unavailable in every configuration or runtime state.

Likewise, the absence of additional entries in this output does not establish that no other services could be enabled by plugins, configuration changes, or alternative runtime states. No requests were sent to either socket, and no application-level behavior, authentication mechanism, route, or protocol exchange was examined.

## 8. Security Characteristics

1. **Wildcard TCP binding:** Port 8443 listens on all IPv4 interfaces in the container's network namespace.
2. **Wildcard UDP binding:** Port 33333 is bound to all IPv4 interfaces in the same namespace.
3. **Shared process ownership:** Both sockets are attributed to the Python management process, PID 1.
4. **Distinct transport behavior:** The TCP socket is listening for connections, while the UDP socket is reported as unconnected.
5. **Exposure remains environment-dependent:** Socket bindings alone do not prove external reachability.
6. **Application behavior remains unexamined:** No requests, authentication tests, route enumeration, or fuzzing were performed.

These observations establish the baseline listener inventory. They do not independently demonstrate a vulnerability.

## 9. Key Takeaways

- The captured `ss -tulpn` output reported two network-facing sockets.
- TCP port 8443 was in the `LISTEN` state and bound to `0.0.0.0`.
- UDP port 33333 was in the `UNCONN` state and bound to `0.0.0.0`.
- Both sockets were associated with `python3`, PID 1.
- The TCP and UDP sockets used file descriptors 11 and 9, respectively.
- No Modbus TCP listener was reported in this snapshot.
- External reachability and application-level behavior were not tested.
- The findings establish a baseline for subsequent research without crossing into HTTP/API testing.

# Phase 4: Runtime Binaries & System Persistence

- **Target Runtime:** OpenPLC Runtime v4
- **Environment:** Isolated Docker container
- **Container:** `openplc-v4-lab`
- **Research Area:** Runtime filesystem layout and state storage
- **Primary Locations:** `/workdir`, `/workdir/build`, `/run/runtime`
- **Objective:** Locate core runtime binaries, configuration files, and runtime databases, and document their observed filesystem characteristics

---

## Executive Summary

This investigation examines the filesystem layout of OpenPLC Runtime v4, focusing on compiled runtime executables, runtime configuration files, and internal state storage.

Filesystem enumeration identified the primary runtime executables at:

- `/workdir/build/plc_main`
- `/workdir/build/etherdog`

The search also identified the EtherDOG source and build directories under `/workdir/third_party/etherdog/`, as well as `/run/runtime/etherdog`, which is a runtime state directory rather than the primary executable.

The runtime state directory contains three notable files:

- `/run/runtime/.env`
- `/run/runtime/etherdog.json`
- `/run/runtime/restapi.db`

The database file was previously identified as SQLite by its file header. The runtime configuration files and database have different observed permission modes, ranging from `0600` to `0644`.

The `/workdir` directory listing shows that the runtime project tree and its top-level files are owned by `root:root`. However, the collected output does not include individual permission details for the compiled executables under `/workdir/build`. Those permissions should not be inferred from the parent directory listing.

This investigation establishes the locations of core executables and runtime state files. It does not establish whether runtime state survives container recreation, whether any file permissions are exploitable, or whether the files contain sensitive values.

## 1. Investigation Scope

## Objectives

- Locate the core compiled runtime executables.
- Identify relevant runtime configuration and state directories.
- Locate SQLite databases used by the runtime infrastructure.
- Record observed ownership and permissions where available.
- Distinguish runtime state files from source code, build artifacts, and test fixtures.

## Scope boundaries

This phase focuses on filesystem layout, executable locations, configuration storage, database files, and observed file permissions.

PLC user-logic compilation, Structured Text or Ladder Logic parsing, IDE build chains, and code translation are excluded from this investigation.

Finding a file does not establish how the application uses its contents, whether it is security-sensitive, or whether it persists beyond the current container lifecycle.

## 2. Core Runtime Binary Locations

### 2.1 Enumeration command

The following command was executed inside the container:

```bash
docker exec -it --user root openplc-v4-lab \
  find / -name "plc_main" -o -name "etherdog"
```

Observed output:

```text
/run/runtime/etherdog
/workdir/build/plc_main
/workdir/build/etherdog
/workdir/third_party/etherdog
/workdir/third_party/etherdog/build/etherdog
```

### 2.2 Binary and directory inventory

| Path | Observed role | Mode | Ownership |
|---|---|---|---|
| `/workdir/build/plc_main` | Compiled PLC runtime executable | `0755` | `root:root` |
| `/workdir/build/etherdog` | Compiled EtherDOG executable used by the observed runtime | `0755` | `root:root` |
| `/workdir/third_party/etherdog/build/etherdog` | EtherDOG executable in the third-party build tree | `0755` | `root:root` |
| `/workdir/third_party/etherdog` | Third-party EtherDOG project directory | See directory listing | `root:root` |
| `/run/runtime/etherdog` | Runtime state directory associated with EtherDOG | `0700` | `root:root` |

The three executable files have owner read, write, and execute permissions, with read and execute permissions for group and other users. Their mode bits do not grant group or other users write access.

The process inspection from Phase 1 identifies `/workdir/build/etherdog` as the executable launched in the observed runtime. The additional executable under the third-party build tree was located, but its equivalence to the active executable was not established.

## 2.3 Interpretation

The runtime's primary compiled executables are located under `/workdir/build`. The filesystem also contains an EtherDOG project tree with a separate executable under its own build directory.

The search results alone do not establish whether the two EtherDOG executable files are byte-for-byte identical or whether the third-party copy is used during normal runtime execution. The process inspection from Phase 1 identifies `/workdir/build/etherdog` as the executable launched in the observed runtime.

The path `/run/runtime/etherdog` is a directory, not the primary EtherDOG executable. Distinguishing it from the executable path prevents runtime state storage from being confused with compiled code.

## 3.3 Interpretation

The actual ability to access or modify individual files also depends on their own permissions, parent-directory permissions, and other access controls.

The top-level listing does not provide enough information to characterize the permissions of the compiled binaries themselves.

## 5. Runtime State Directory

## 5.1 Observed layout

The Phase 2 filesystem inspection identified the following entries under `/run/runtime`:

| Entry | Observed mode | Ownership | Role or evidence |
|---|---|---|---|
| `.env` | `0600` | `root:root` | Environment file; contents not read |
| `etherdog/` | `0700` | `root:root` | Runtime state directory |
| `etherdog.json` | `0600` | `root:root` | Runtime configuration file |
| `etherdog.socket` | `0600` | `root:root` | Unix-domain control socket |
| `log_runtime.socket` | `0755` | `root:root` | Unix-domain logging socket |
| `plc_runtime.socket` | `0755` | `root:root` | Unix-domain PLC runtime socket |
| `restapi.db` | `0644` | `root:root` | SQLite database file |

The socket entries are included to show the runtime directory's overall structure. Their communication roles and access-control caveats are documented in Phase 2.

## 5.2 Interpretation

The runtime state directory contains configuration, database, and IPC artifacts alongside the EtherDOG state directory.

The observed permission modes differ between files. Under the standard Unix permission model, mode `0600` grants read and write permissions to the owner only, while mode `0644` grants read access to group and other users. These mode bits do not account for additional access-control mechanisms or filesystem-level restrictions.

The `0644` mode on `restapi.db` therefore indicates that the file's mode bits permit reading by users other than the owner, assuming the relevant directory permissions and other access controls allow access. This is an access characteristic, not proof that the database contains sensitive information or that unauthorized disclosure has occurred.

Similarly, the presence of `.env` does not establish that it contains credentials or other secrets. Its contents were not inspected in this phase.

The directory's location under `/run` identifies where the runtime state was observed. The evidence collected here does not establish whether these files are recreated at startup, retained across container restarts, or stored on persistent volumes.

## 6. SQLite Database Identification

## 6.1 Inspection procedure

The first 16 bytes of the database file were inspected using:

```bash
docker exec -it --user root openplc-v4-lab \
  od -An -N16 -tc /run/runtime/restapi.db
```

The output contained the SQLite file header:

```text
SQLite format 3
```

## 6.2 Observations

- `/run/runtime/restapi.db` exists in the runtime state directory.
- Its file header identifies it as an SQLite database.
- The previously observed file size was 16,384 bytes.
- Its observed mode was `0644`.
- It was owned by `root:root`.

## 6.3 Interpretation

The file header confirms the database format. The filename and location associate the file with the runtime infrastructure, but the header alone does not establish the database schema, the information stored in its tables, or which runtime component reads or writes it.

No conclusions about database contents or application-level authorization are drawn from file identification alone.

## 7. File Permission Characteristics

The observed permissions establish several filesystem-level characteristics:

1. **Root-owned project tree:** The displayed top-level project entries are owned by `root:root`.
2. **Executable project scripts:** The top-level listing shows executable permission bits on `install.sh` and `start_openplc.sh`.
3. **Restricted runtime configuration files:** `.env` and `etherdog.json` were observed with mode `0600`.
4. **Restricted EtherDOG state directory:** `/run/runtime/etherdog` was observed with mode `0700`.
5. **Database readability by mode:** `restapi.db` was observed with mode `0644`, which permits read access to group and other users at the mode-bit level.
6. **Binary permissions not individually captured:** The current output establishes the executable locations but does not show the individual mode bits or ownership of `/workdir/build/plc_main` and `/workdir/build/etherdog`.

These findings describe the captured filesystem state. They do not independently establish a privilege-escalation path, unauthorized file access, persistence across container recreation, or a security vulnerability.

## 8. Security and Reliability Significance

The investigation establishes the locations of the main compiled runtime executables and several files used by the runtime infrastructure.

The placement of runtime binaries under `/workdir/build` distinguishes executable artifacts from the source and third-party project trees. The files under `/run/runtime` represent a separate collection of runtime configuration, state, and IPC artifacts.

The observed ownership and permissions provide a baseline for understanding which filesystem entries are restricted by mode bits. A complete access assessment would also depend on the process execution identity, directory traversal permissions, mounted filesystems, container configuration, and any additional access-control mechanisms.

No user-logic compilation or code-translation behavior was examined. No claim is made about the persistence of runtime state beyond the observed container session.

## 9. Key Takeaways

- The primary compiled runtime executables were located at `/workdir/build/plc_main` and `/workdir/build/etherdog`.
- An additional EtherDOG executable was found under `/workdir/third_party/etherdog/build/`.
- `/run/runtime/etherdog` is a runtime state directory, distinct from the compiled executable.
- The runtime state directory contains `.env`, `etherdog.json`, and `restapi.db`.
- The database file was identified as SQLite using its file header.
- `.env` and `etherdog.json` were observed with mode `0600`; `restapi.db` was observed with mode `0644`.
- The top-level `/workdir` entries shown in the listing were owned by `root:root`.
- Individual permission details for the primary compiled binaries were not included in the captured output.
- The filesystem search identifies where relevant files reside but does not establish database contents, secret exposure, or persistence across container recreation.

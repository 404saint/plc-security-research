# Phase 7: Real-Time Scheduling & Resource Isolation

- **Target:** OpenPLC Runtime v4
- **Environment:** Isolated Docker lab
- **Container:** `openplc-v4-lab`
- **Primary Process:** `plc_main` (PID 878)
- **Scope:** Scheduling policy, thread priorities, CPU affinity, and cgroup resource limits
- **Method:** Read-only runtime inspection

---

## Executive Summary

This investigation examined the scheduling configuration and resource constraints of OpenPLC Runtime v4 running inside the lab container.

The inspected `plc_main` process uses the standard Linux `SCHED_OTHER` scheduling policy with priority `0`. All four listed threads use the normal time-sharing scheduling class, and none has a reported real-time priority. The process affinity mask is `fff`, indicating that its allowed CPU set is not restricted to a single CPU by the inspected process affinity setting.

The container's inspected cgroup files report no explicit CPU quota or memory maximum at that level. These findings establish the observed scheduling and resource configuration, but they do not demonstrate deterministic execution, bounded cycle times, or consistent performance under system load.

## 1. Scheduling Policy and Thread Priorities

## 1.1 Inspection Method

The scheduling policy and thread information were collected using `chrt` and `ps` inside the running container.

```bash
docker exec -it --user root openplc-v4-lab sh -c \
'for pid in $(pgrep plc_main); do
    echo "=== PID $pid ==="
    chrt -p $pid
    ps -T -p $pid -o spid,cls,rtprio,ni,comm
done'
```

## 1.2 Observed Results

The inspected process reported:

```text
=== PID 878 ===
pid 878's current scheduling policy: SCHED_OTHER
pid 878's current scheduling priority: 0

SPID  CLS  RTPRIO  NI  COMMAND
878   TS   -       0   plc_main
879   TS   -       0   plc_main
880   TS   -       0   plc_watchdog
888   TS   -       0   plc_main
```

The output identifies four threads associated with the process:

- PID 878: `plc_main`
- PID 879: `plc_main`
- PID 880: `plc_watchdog`
- PID 888: `plc_main`

The `TS` class denotes the normal time-sharing scheduling class. The dash in the `RTPRIO` column indicates that no real-time priority is reported for these threads.

## 1.3 Interpretation

The inspected process uses `SCHED_OTHER`, rather than a real-time scheduling policy such as `SCHED_FIFO` or `SCHED_RR`.

This means the captured configuration does not show the PLC process or its listed threads receiving real-time scheduling priority. Their execution is managed by the standard Linux scheduler.

This observation matters for industrial control workloads because execution timing can be affected by competing tasks, host activity, and scheduler behavior. However, the scheduling policy alone does not establish whether the runtime meets or fails any particular cycle-time requirement.

## 2. CPU Affinity

## 2.1 Inspection Method

The process CPU affinity was inspected using:

```bash
docker exec -it --user root openplc-v4-lab sh -c \
'for pid in $(pgrep plc_main); do
    echo -n "PID $pid Affinity: "
    taskset -p $pid
done'
```

## 2.2 Observed Results

```text
PID 878 Affinity: pid 878's current affinity mask: fff
```

## 2.3 Interpretation

The hexadecimal affinity mask `fff` represents twelve CPU positions, corresponding to CPU IDs 0 through 11 when those IDs are available in the process's effective CPU namespace and allowed set.

The inspected affinity setting therefore does not pin the process to a single CPU. Instead, it allows execution across the CPUs represented by the mask.

The mask alone does not prove that all twelve CPUs are available to the container at the host level or that the process actually ran on each one. The effective allowed CPU list and any parent cgroup restrictions would need to be considered for a complete host-level assessment. No dedicated-core assignment is demonstrated by this result.

## 3. CPU and Memory Resource Limits

## 3.1 Inspection Method

The container's cgroup resource settings were inspected using:

```bash
docker exec -it --user root openplc-v4-lab sh -c \
'echo "CPU Max:"
cat /sys/fs/cgroup/cpu.max 2>/dev/null || cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us
echo "Memory Max:"
cat /sys/fs/cgroup/memory.max 2>/dev/null || cat /sys/fs/cgroup/memory/memory.limit_in_bytes'
```

## 3.2 Observed Results

```text
CPU Max:
max 100000
Memory Max:
max
```

## 3.3 Interpretation

The CPU setting `max 100000` indicates that no CPU bandwidth quota is configured in the inspected cgroup's `cpu.max` file. The `100000` value is the quota period in microseconds; `max` means the quota is not capped at that level.

The memory setting `max` indicates that the inspected cgroup has no configured maximum memory limit in its `memory.max` file.

These findings do not establish that the container has unlimited access to system resources. Parent cgroups, Docker CPU or memory settings, CPU-set restrictions, host contention, and available physical resources can still constrain execution. The inspection also does not measure actual CPU utilization, memory consumption, throttling, or behavior under resource pressure.

## 4. Security and Reliability Considerations

The observed configuration provides several useful baseline findings:

- **Standard scheduling:** The inspected PLC process and its listed threads use the normal time-sharing scheduling class.
- **No observed real-time priority:** The thread listing does not show `SCHED_FIFO`, `SCHED_RR`, or assigned real-time priorities.
- **No single-core pinning:** The process affinity mask permits more than one CPU.
- **No explicit limits at the inspected cgroup level:** The CPU and memory files do not show configured maximum quotas or limits.

These are configuration observations, not direct evidence of a vulnerability or runtime failure.

In particular, the absence of a CPU quota does not establish that the PLC will be starved of CPU time, and the absence of a real-time scheduling policy does not by itself prove that execution deadlines will be missed. Those conclusions would require performance measurements and defined timing requirements.

Likewise, this investigation did not measure PLC scan-cycle duration, scheduling latency, jitter, deadline misses, CPU saturation, or memory pressure.

## Key Takeaways

1. The inspected `plc_main` process uses `SCHED_OTHER` with scheduling priority `0`.
2. All four listed threads use the normal time-sharing class, with no reported real-time priorities.
3. The process affinity mask is `fff`, allowing execution across the represented CPU set rather than pinning the process to one CPU.
4. The inspected cgroup reports no CPU quota and no memory maximum.
5. These settings do not prove deterministic execution or failure to meet timing requirements. Measuring scan-cycle consistency and scheduling behavior under load would be necessary to assess real-time performance.

The scheduling and resource-isolation baseline is documented. No scheduling changes or load tests were performed.
